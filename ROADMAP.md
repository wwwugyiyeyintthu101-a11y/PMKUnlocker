### 2.2 Measured wire facts (the parts that must not be re-derived)

- **Two protocol layers, opposite endianness.** BROM/preloader is big-endian (`0xFD` HW code, `0xD4` watchdog, `0xD8` target config, `0xDA`/`0xD1` register access, `0xD7` DA1 upload, `0xC0` DA1 alive). DA is little-endian with magic `EF EE EE FE`, `type u32le = 1`, `length u32le`, then payload.
- **DA framing is two writes, never merged.** Every command is the 12-byte header, then the 4-byte id as its own write; the host ack is a 4-byte zero in its own frame. Both boot recordings (mt6765: 51 command frames, MT6877: 51) show this split. RUN B6-4's MT6877 DA answered the split shape 17 times and refused the merged 16-byte transfer — the old merged helper was our invention, not the recording's.
- **Command ids in use:** `0x10003` ERASE, `0x10004` WRITE, `0x10005` READ, `0x10008` upload+jump, `0x10009` preamble (31× before op groups), `0x1000A` EMI/DRAM, `0x40001` storage descriptor (104 B), `0x40004` UFS geometry (208 B), `0x40007` transfer limits, `0x4000A` `"brom"`, `0x4000B` `"high-speed"`, `0x40011` DA version, `0x40016` SLA state, extensions `0xF0000`/`0xF0005`.
- **The 56-byte extent struct** (READ/WRITE/ERASE): `u32le region`, `u32le field4`, `u64le offset`, `u64le length`, 32 zero bytes. The pair is **not a constant**: MT6765 eMMC uses `1 + 8`, MT6877 UFS uses `0x30 + 3`; both were measured against the unit's own READ structs and both equal the first word of that unit's geometry reply.
- **Write path:** `0x10009` → `0x40007` → `0x10004` + struct → per `0x200000` chunk two 4-byte frames (`0x0`, then a checksum) + data, one status each → `0x10009` → `0x80005` (no argument) → status → 4-byte status. The checksum is **Σ bytes mod 65536, sent as u32** — not a CRC.
- **Read path is frame-driven:** header + payload + host ack + status, repeated until the requested byte count is reached (a 2 MiB read is 32 frames at the DA's `0x40007` packet limit). Acking once at the end hangs on every partition dump above 64 KiB.
- **Erase path:** bare `0x10003` + struct (no `0x10009` preamble, no limits query), then report words `0x40040004`, `0x64`, host ack, `0x40040005` — loop on the report, do not hard-code two words.
- **Control probes are real protocol.** Before each pre-download jump the working client sends a CDC `SET_LINE_CODING` (accepted) and a vendor `GET_DESCRIPTOR` (stalled), with extension words `91C2, 92C2, 93C2, 8AC2, 89C2, 88C2`. This is the traffic no bulk trace or command log could see; without it the BROM refuses step 65 with `0x1D1A`.
- **Greeting is a hardware step.** Four one-byte pairs `A0/0A/50/05` each answered by its complement, then the recipe's own `0xFD`. A face already past the greet answers `A0` with itself; the HW code still decides.
- **Stale DA lies.** A phone with a DA still in RAM re-enumerates as `0E8D:0003` and answers `0xFE`; PnP cannot tell it from a BROM. Fail closed when the boot did not visibly walk BROM (real menu Power off + BOTH volume keys).
- **UFS geometry:** `0x40001` answers 104 zero bytes on a UFS unit; `0x40004` answers 208 bytes: region `0x30`, block 4096, boot LUN1/LUN2 4 MiB, user area at +24 (`0x3B96000000` on the capture), then disk identity at +32 which is **never decoded or stored**. RPMB and general-purpose areas have no measured slot and stay 0.
- **Control asks can hang.** RUN B6-1: the post-payload `SET_LINE_CODING` went out and never completed; the phone re-initialised and left the bus. Every ask is therefore bounded by timeout + 1 s, a no-answer is a fourth state (`CtrlNoAnswer = -1000`), and an abandoned transfer is watched and reported late instead of being dropped.

### 2.3 Recipes (`mtk/boot-profiles`)

- One JSON per chipset, flat ordered `tx` / `rx` / `blob` / `ctrl` steps plus hash-pinned blobs. The loader is fail-closed: every blob is size- and sha256-verified, every framed upload's header must match the file, and a wrong HW code stops the boot.
- `"opt": true` on a `ctrl` step marks a step the recorded boot accepted but the boot does not depend on (the two MT6877 line-setting probes). An optional step that cannot be carried is logged and stepped over **on the pipe in hand** — no reclaim, no dispose, because the greet after it needs the live pipe.
- Master copy lives at `%LOCALAPPDATA%\PMKMobileTool\mtk\boot-profiles`; the `CopyMtkBootRecipes` build target copies it into every output (override `-p:MtkRecipeSource=<folder>`). Without the folder the NATIVE tab is absent by design.
- The recipes and blobs are **not tracked in git and not shipped**. Licensing decision remains open (see §7).

### 2.5 Guards implemented (must stay)

- `NeverProgramNames` (`pgpt`, `sgpt`, `gpt`, `otp`, `flashinfo`) — brick guard.
- `ReadOnlyPayloadNames` (`seccfg`) — no measured program payload; read stays open.
- Extent checks: block alignment, zero length, past-end-of-user-area, using the DA's own block size.
- One client per BROM: native session and mtkclient workflows refuse each other (`Eject Device first`).
- Confirmation dialog shows the exact extent, image and readback promise before any write.
- Write verify: every native write is read back and compared; a mismatch marks the partition damaged.
- Device-bound GPT cache only (`SaveMediaTekGptCache` refuses unbound tables; `LoadMediaTekGptCache` deletes one it finds).
- Identity policy: eMMC part number is the only identity-adjacent field shown; CID serial, UFS product/serial and chip-unique ids are never decoded, stored or logged.

## 4A. P1.1 + P1.2 — native GPT save and native partition backup (2026-11-05, hardware-proven — and the run found a 50× read stall worth more than either button)

**What the two buttons do now.** Both are the SERVICE/FLASH buttons that already existed — `📋 Save GPT` and the two `Backup` buttons — and each now asks one question first: *is a native DA session live?* If it is, the work goes through that session; if not, the unchanged `mtk.exe` route runs. No new button, no new dropdown, and the batched route stays as the fallback for a chipset with no recipe.

- **P1.1 — one READ replaces one boot.** `ReadPartitionTableAsync` already reads the primary header (one block at byte `block`) and the whole entry array into memory, so the save costs exactly one extra read: the backup array and its header, at the LBA the primary header itself names. `MtkDaSession.SaveGptAsync` reuses the cached table when the boot already filled it, so a post-boot save touches the wire only for that one extent.
- **P1.2 — six boots become six reads.** The batched path shells `mtk.exe r <name> <file>` once per partition, and each of those is a full boot (~34 s on this bench, so the six NV partitions ≈3.5 minutes of replugging). The native path does one `ReadPartitionToFileAsync` per name over the session that is already open, then writes the manifest with the same `ShopServices.WriteBackup` call and registers it with the same `RegisterBackup` — so a folder produced natively restores through the restore path that already ships, unchanged.
- **The read list and the manifest are one map.** `MtkNativeBench.BackupLayout` takes the device's own extents and produces the `{name → size}` dictionary both the reads and `WriteBackup` consume, so the sizes recorded in the manifest *are* the extents the reads were addressed with — a second, independently derived claim about the phone would have been free to contradict the first. A name absent from the device's GPT refuses the whole operation before any frame goes out, and the refusal says how many entries were read.

**The folder format is ours, and that is a provenance statement, not a shortcut.** `gpt-layout.json` / `gpt-primary-header.bin` / `gpt-primary-entries.bin` / `gpt-secondary.bin` / `gpt-sha256.txt` were recovered from this repo's own deleted `PMKUnlocker/pmk_gpt.py` (`git show 69f385a^:PMKUnlocker/pmk_gpt.py`) and cross-checked against samples that still survive under `%LOCALAPPDATA%\PMKMobileTool\Backups\preloader-<hash>\`. The field offsets and the CRC rule are the published UEFI 2.10 §5.3 layout. **No mtkclient source was read for either item.**

**What refuses and what only speaks.** Geometry errors refuse the save — no `EFI PART`, a header smaller than the device's block, a `headerSize` outside the read buffer, an entry array that doesn't fit what the header claims, a header that doesn't call itself LBA 1, or a backup LBA that overlaps the primary array. The two UEFI CRC verdicts and whether the backup LBA equals the last LBA of the user area are **recorded and printed, never enforced**, because this tool has never read a UFS GPT through its own session — a mismatch on a first UFS snapshot is information about the decoder, not danger to the phone.

**Two invariants the tests now hold:**
- `EnterOperation`/`LeaveOperation` do **not** nest. `ReadPartitionTableAsync` was split into a guard wrapper plus a private `ReadPartitionTableCoreAsync` precisely so `SaveGptAsync` can hold the port and still read the table; a future caller that grabs the guard twice will fail the check, not silently double-leave it.
- The last `await` before a `FolderBrowserDialog` must **not** use `ConfigureAwait(false)`, or the modal runs on a thread-pool thread. `NativeBackupAsync` reads the table without it for that reason, and the comment says so; `NativeSaveGptAsync` picks its folder before any await, which is the other safe order.

The probe checks that a read reports its own extent's frame and byte counts, that a scripted device with bytes ready charges zero empty waits, and that the counters reset per read instead of accumulating. **The hash chain the ROADMAP asked for** ("hash before/after") is transitive and all three links are on disk in this log: manifest SHA-256 → file on disk (`VerifyBackup` re-hashes every file before the dialog is even built) → device extent (`VERIFY OK` compares the read-back against the bytes just written). Device bytes therefore equal manifest bytes for all six partitions, proven per extent rather than by a layout hash.

**Why the layout hash is deliberately not compared.** `ShopServices.VerifyBackup(dir, deviceLayout)` enforces `manifest.LayoutHash == LayoutHash(deviceLayout)`, but a native NV manifest hashes the six names it read and an mtkclient NV manifest hashes the whole 43-entry table — the two kinds of folder would reject each other's `LayoutHash` while both being equally good to restore from. The native route therefore calls `VerifyBackup(srcDir)` with **no** device layout and lets `MtkNativeBench.NvRestorePlan` enforce per-extent byte equality itself, which also lets a 43-entry mtkclient manifest serve a six-name NV restore.

**Refusals that were not exercised on this phone but are pinned by checks:** a name missing from the device's own GPT, a manifest size that disagrees with the extent, `gpt`/`seccfg` riding along inside an NV set (`ProgramAllowed` refuses the **whole** set before the first frame, never four of six), and a folder with no `backup-manifest.json` — each spends zero frames and says so.

**One dialog per operation, both routes.** `NV Reset`, `NV Erase` and `NV Restore` each ask exactly once: the Yes/No that names what is and is not touched sits in front of the route branch, and the native restore's own detail dialog (extent list + source folder + the raw-write honesty note) is the only prompt on that route because the mtkclient prompt moved into the mtkclient branch. PMK saw one dialog per click on all three buttons in this run.

## 4C. P1.4 — Firmware Backup (Scatter) (2026-11-06: hardware-proven — 4-partition dump + re-flash, 43-row package, phone booted)

A dump folder is a pile of images until something says which byte of the device each one belongs to. The BACKUP tab's `💾 Backup Selected` now writes that index — a real MTK scatter — beside the images, so the same folder can be loaded on the FLASH tab and re-flashed as a firmware package.

**One button, two artifacts.** PMK's rule on this tab is one button per job, and the job (`dump the partitions I ticked`) already had a button. The scatter is therefore an output of `Backup Selected`, not a second route to the same reads: same folder, same `<name>.bin` files, same `ShopServices.WriteBackup` manifest, plus one generated `<chipset>_scatter.txt`. The NV button keeps its six-image folder shape — a six-partition NV set is not a firmware package, and labeling it one would be exactly the kind of artifact the operator then has to interpret.

**The size was measured before the design was agreed**, decoded from the 43 extents of the GPT folder P1.1 saved (`GPT-27101e056d7f49279d0f38a79f96ca4d`, block 512):

| ticked set | extents | bytes | read time at the measured 8.7 MB/s |
|---|---|---|---|
| all | 43 | 62,528,127,488 (58.23 GiB) | ≈2 h |
| all except `userdata` | 42 | 6,915,325,952 (6.44 GiB) | **≈13 min** |
| − `cache`, `metadata` | 40 | 6,428,786,688 (5.99 GiB) | ≈12.3 min |
| − `cust` and `super` too | 38 | 724,533,248 (691 MiB) | ≈1.4 min |

`userdata` alone is 51.7 GiB and `super` alone 4.6 GiB — 66 % of everything left once userdata is out. So the honest statement about a "full firmware backup" on this bench is **one ticked grid, ≈6.4 GiB of flat images, ≈13 min of reads, and the disk space to hold it**; there is still no "dump everything" button, and a raw dump does not sparse-trim `super`.

**The unit is bytes, and that is the check that exists for it.** A scatter's `linear_start_addr` / `partition_size` are byte offsets, while the live table is LBA pairs — the same conversion `MtkDaExtent.ByteOffset` already does for the DA's own extent structs. Writing an LBA where a byte address belongs would not fail: every row of the package would program a different partition than the one it names. The P1.4 checks pin the conversion against the device's own `boot` extent (LBA `0x2b9400` × 512 = `0x57280000`, `0x4000000` long) and then read the file back through `ScatterParser` to prove the hex survives the round trip.

**What the writer refuses, and why each refusal is a real failure mode.** `ScatterWriter.Build` throws instead of emitting a row when a name or file name carries `:`, a newline, a path separator, a `..` segment or leading/trailing space (the reader splits each line on its first colon, so one device name could otherwise become two keys — or a whole injected row); when a partition name repeats (the reader drops the second row, so its image would silently never be written); when two rows share bytes in one region; when an extent is zero-length; when the region is one the reader does not know; and when the chipset is missing (the reader would reject the entire file as an unsupported scatter). A name the live GPT does not report stops the scatter too — an invented offset is a write list aimed at the wrong bytes.

**`is_download: false` is the same gate the session already obeys.** `otp`, `flashinfo` and `seccfg` are dumped and listed — with their real offsets and their file names — but marked non-download, because `ProgramAllowed` refuses to write or erase them through a live session (`otp`/`flashinfo` = never-program list, `seccfg` = read-only since B5.9). A package that offered to rewrite the chip identity would be a package that bricks the phone it came from, and preflight confirms the refusal holds: selecting `otp` out of a generated package is reported as a mismatched image rather than flashed.

**UFS gets its images, not a scatter.** The region word a UFS scatter carries (`UFS_LU0`-class) has never been read off a real package on this bench, and `ScatterParser` only knows the EMMC region names — an invented one would either be rejected by our own reader or, worse, accepted and aimed at the wrong area. The MT6877 route therefore says plainly that the dumps and manifest are saved and no package file is written.

**The mtkclient route on this button is now one session, not one boot per partition.** It used to loop `mtk.exe r <name> <file>` once per partition — one python process, one full BROM boot, and one replug, each time. For a 42-partition firmware set that is 42 boots. The fallback now runs `printgpt;r <name> <name>.bin;…` as one `multi` script, parses the GPT from that same run, verifies every staged file against the length the GPT reported, moves the images into the `MTK-<guid>` folder, writes the same manifest, and then writes the same `<chipset>_scatter.txt` from that GPT (eMMC only; a UFS or unreported storage keeps its images and manifest and gets no scatter). A chipset with no native boot recipe can therefore still produce a firmware package from one boot; the native route stays the faster one when a session is already open because it reads over the session it has rather than booting again. **Hardware-proven 2026-11-06:** `recovery` + `para` in one `multi` session (`09:16:51 → 09:17:12`, one BROM connect, two `Dumping partition` lines), then the generated 43-row package re-flashed through mtkclient (`09:17:31 → 09:17:47`, 2 writes, 64.50 M, 15 s, no removal warning) — §4D.

**The 2026-11-05 hardware run found two defects — the first stopped the flash before a single write.** The dump of `recovery`, `frp` and `logo` wrote `MT6765_scatter.txt` correctly by our own parser's rules, and the FLASH tab loaded it as three rows. `wfscatter` did not: it printed `DaHandler - [LIB]: Scatter has no partitions.` and PMK's evidence check turned that into `[FAIL] recovery / frp / logo — write not confirmed`, with the cause missing from the screen. Root cause: the writer emitted the YAML **list** form (`  - partition_name: recovery`); the client strips each line, splits on the first colon and keeps the key verbatim, so every key was `- partition_name` and no row was parsed. The writer now emits the stock MTK **mapping** form (`  partition_name: recovery`), the same dialect vendor scatters use, and a regression check runs the client's own grammar over the generated file instead of only our lenient parser.

**The second defect was latent and would have been destructive.** `wfscatter` rebuilds the GPT from the rows it parsed and prints `Warning: device partitions not in scatter will be removed: …` for the rest. A three-row dump therefore did not merely re-flash three partitions — it would have rewritten the phone's 43-entry table down to those three, with the gap-fill stretching `recovery` to the next start. The scatter now carries **every live extent**: the dumped partitions as image rows, every other one as `is_reserved: true` / `operation_type: RESERVED` with `file_name: NONE`, whose extent the client re-reads from the live table. A partial dump is now a partial write against an unchanged table, which is what "re-flash this dump" was always supposed to mean.

**And the failure was silent on screen.** `MapMtkMstLine` is a milestone table that dropped every unmapped line, including the client's own coloured `[LIB]` error. Red `[LIB]` lines now print as `! …` in red and yellow ones as warnings, so a failed operation names its reason before the `[FAIL]` summary.

**The reset's own `[LIB]` line is not a flash failure.** The 2026-11-06 run surfaced `DAXFlash - [LIB]: Stage was't executed. Maybe dram issue ?.` after the last write. It follows `PMK reset: rebooting via TOPRGU stub at 0x4fff0000 (56B)` and `USBError(5, 'Input/Output Error')`: the chip reset drops the USB link mid-handshake, and mtkclient's DAXFlash reports that as a stage error. The 2.2.9 lock note already records the same line on a run whose phone booted, so it is expected reset noise, not DRAM. The display now suppresses that one line only after PMK's reset marker has been seen; a `Stage was't executed` before any reset still prints as a red `!`, and `last-run.raw.log` keeps every line.

**The 2026-11-06 re-run closed both defects on hardware.** `08:38:26–08:38:36` — `Backup Selected` on the 9A dumped `recovery` (64 MiB), `frp` (1 MiB), `boot` (64 MiB) and `logo` (8 MiB) into `MTK-dd7340900b9e4cebb988618b9282bd09` and wrote `MT6765_scatter.txt` with **43 rows**: the four images as `is_reserved: false` and the other 39 live extents as `is_reserved: true` / `operation_type: RESERVED` / `file_name: NONE`. `08:39:48–08:40:06` — the FLASH tab loaded the package as four rows at `0x108000`, `0x3bd88000`, `0x57280000`, `0x5b280000`; the one-plug `wfscatter` run updated **both GPTs**, wrote all four images (`recovery` sector 2112/131072, `frp` 1961024/2048, `boot` 2855936/131072, `logo` 2987008/16384), printed **no** `device partitions not in scatter will be removed`, sent the reset, and finished at `137.00 M / 18 s`. The 9A booted to the Android home screen. The old `MTK-9662448d...` three-row folder remains the broken list-form artefact and must not be flashed.

Regression **823** at the P1.4 batch (+28): the byte-unit round trip (both address fields — `linear_start_addr` and `physical_start_addr` must carry the same offset, because a prefix-less number is read as decimal), the row-per-dump mapping, both `is_download` verdicts, the UFS and missing-name refusals, the package file name matching the FLASH tab's own `*scatter*.txt` filter, a re-parsed package whose selectable rows are exactly the dumped-and-allowed ones, no overlap and no blocking error in a self-made package, preflight accepting it, and every build-time refusal (colon, newline, traversal, duplicate, overlap, zero length, unknown region, empty platform). ## 4D. P1.5 — native multi-partition flash + single-session fallback (hardware-proven 2026-11-06, both routes)

**The native route.** With a live DA session, `💾 Flash Selected` no longer shells out to `mtk.exe`: `FlashMediaTekAsync` branches to `NativeFlashAsync` before the mtkclient confirmation. The write list is resolved against the cached live GPT first (`MtkNativeBench.NativeFlashPlan`), and every row must agree with the device's own extent in **both** offset and length. That equality is the gate, not a formality: the native path writes by partition name and never rebuilds the GPT, so a package from another layout is not a smaller version of the job — it is a write list aimed at bytes this phone may not own. The plan also refuses a never-program name (`otp`/`flashinfo`/`seccfg`), an image larger than its extent, a missing image, a duplicate name, and an empty selection. A sparse image is accepted by expanding and validating it on the PC before **any** partition is written (`NativeFlashPreparation`: temporary space pre-checked against the free bytes, don't-care ranges zeroed, expanded length re-checked, temp raw files removed when the operation ends) — the DA still sees raw bytes only, and the confirmation names the temporary bytes the expansion costs. One dialog covers the whole set, then the writes run one after another with the proven per-write readback (`WritePartitionAsync(..., verify: true)`), followed by exactly one reboot.

**The fallback.** `Backup Selected` without a live session is the single-`multi` flow described in §4C: `printgpt;r <name> <name>.bin;…` in one boot, exact-size check against that run's GPT, manifest via the same `ShopServices.WriteBackup`, then `<chipset>_scatter.txt` via `MtkNativeBench.ScatterRowsFromGpt` (eMMC only; UFS and an unreported storage are refused rather than guessed). ### 4E. P1.6 — the startup prune of failed-session folders (2026-11-06, code done, 7 checks)

**Why.** The mtkclient adapter deletes its `MediaTekSessions\<guid>` folder after a successful run, so the folders that survive are the failures and the crashes — and the staged `.bin` dumps inside them are what once grew that tree to **52 GB**. Nothing ever pruned them; the 2026-10-28 manual clean-up freed the symptom once and left the cause in place.

**The rule that keeps it safe.** `MtkSessionPrune.Prune` (`PMKUnlocker/MediaTek/MtkSessionPrune.cs`) considers **GUID-named folders only**. `seccfg-backup`, its `archive-20261013` child, the `native-da` bench folder and every future hand-named folder are not GUIDs, so they cannot become candidates — a blocklist would go stale the day a new protected name lands; the shape check cannot. The newest **15** survive (post-mortem room), the rest are deleted, and a locked file keeps its folder for the next startup to retry. It runs once at startup in the background (`Form1`, fire-and-forget `Task.Run`, before any engine exists, so no live session can be inside a candidate), and it logs one line only when it actually pruned something.

**What is pinned without hardware.** 7 checks: keep-newest by write time, bytes freed counted from the staged files, `seccfg-backup` / `archive-20261013` / `native-da` untouched, the newest kept and the oldest gone, a second run deleting nothing, a data directory that never held a session not being an error, and a negative keep refused rather than deleting everything. No hardware is owed: this code never touches a device. Debug/Release **0/0**; regression **846** (+7).

### 4G. P1.8 — ADB post-flash verification (2026-11-06 code; **hardware-proven 2026-11-07**, 16 checks)

**Why.** Every flash / Format All / NV restore ends with the DA resetting the phone, and the only honest proof that the operation did not leave it at the logo used to be a human watching for the launcher and typing `*#06#`. That is the one step the tool could not report on, and it is exactly the step that decides whether the job is finished.

**What it does.** `MtkPostFlashCheck` (`PMKUnlocker/MediaTek/MtkPostFlashCheck.cs`) asks Android once per poll with `adb shell getprop`, parses the `[key]: [value]` dump, and answers three states: `BOOTED` (`sys.boot_completed=1`), `STILL BOOTING` (ADB answers, the framework is not up) and `NO ADB`. The result prints as **one aligned block** — a `[OK]`/`[!] Verify Boot — VERDICT` header, then `Boot` / `Device` / `Serial` / `Verified` / `IMEI` / `Note` rows — so a run reads as one answer instead of twelve timestamped sentences, and the poll loop only logs the first poll, a state change and every tenth poll (a three-minute wait is ~9 lines, not 45). The wait is bounded (3 minutes, one poll every 4 s), the ADB call and the delay are delegates, and the operator's cancel aborts the wait instead of being mistaken for ADB's own timeout. The rows name the model/build, `ro.boot.verifiedbootstate` (with `orange` decoded as "bootloader unlocked") and `ro.boot.flash.locked`, and the IMEI it can read — **masked to its last four digits at the source**, so no caller can log the full identity. It also names what the check cannot prove: the FRP state is not an ADB property, and many builds hide `persist.radio.*` from a non-root shell, so a missing IMEI is reported as missing rather than as "intact". The button is `✅ Verify Boot (ADB)` on the INFO tab's SERVICE frame (Read Info, Save GPT, Verify Boot), it refuses to poll while a native DA session is still live, and every native reboot now logs the one-line pointer to it.

**What is pinned without hardware.** 16 checks: parsing (the adb banner dropped, every `[key]: [value]` kept), the boot flag, the IMEI preference (`imei1` → `imei` → `imei2`), masking (15 digits, short, empty), the report's masked output and its "cannot prove FRP" limit, the still-booting / missing-key report (the IMEI group named once, readably), the orange verified-boot decode, and the poll loop's six shapes: stop on the first `sys.boot_completed=1` (and report which poll answered), spend the whole budget without calling it booted, no ADB at all, an ADB timeout as an unanswered poll, a zero-length window asking exactly once, and the operator's cancel propagating. Debug/Release **0/0**, solution **0/0**; regression **945** (+16).

**Hardware run 2026-11-07 08:50:09 (PMK's click, Redmi 9A / M2006C3LG, Debug exe, phone already on Android).** The check answered on **poll 1** — `sys.boot_completed=1`; `device = Xiaomi M2006C3LG (Android 10), build QP1A.190711.020`; `serial = 5TUW8T75JJ5PGURC`; `verified boot = orange, ro.boot.flash.locked = 0`; and **no IMEI property was readable**. That last line is the honest-limit path doing its job: the report said this build hides `persist.radio.*` from a non-root shell and pointed at `*#06#`, instead of claiming the IMEI was verified. `orange` + `flash.locked = 0` is the phone's unlocked-bootloader state — reported as a state, not as a flash verdict. Final line: `[*] Verify Boot: BOOTED.` So the whole chain (button → bounded poll → `getprop` parse → verdict → masked report) is proven on a phone, and the "missing IMEI" branch is proven too.

## 7. Constraints & safety rules

- **Licensing (MTK native):** mtkclient is GPL-3.0. The native session is clean-room from the public SP-Flash-Tool protocol and observed wire traffic — never translated from `xflash_*` source. Reading a GPL program's output is observation; do not open its source while implementing.
- **Licensing (blobs):** OEM-signed DA/auth/firehose/FDL blobs are proprietary. The current packs are unlicensed re-hosts — decide whether to ship, drop or source them legally. The native recipes (`mtk/boot-profiles`) are in the same position and are not tracked or shipped.
- **Never commit** `mtk/boot-profiles`, `bundled-tools/`, `tools/` or `edl/`; the rollback reference for loader binaries is `bundled-tools/integrity.json` + `dependency-lock.json`. After any loader change: `scripts/make_tool_integrity.ps1` → sync `bundledInventory.sha256`/`entries` → Release build → `scripts/verify_qc_loaders.ps1`.
- **Never copy** a differently-named Common DA into an existing loader folder — it silently replaces a working DA; hash-check against the seed first.
- **MTK loader rule:** never auto-pass a catalog `--loader` over mtkclient's built-in DA by default — the xflash DA-extension patch path only works with the DA mtkclient bundles itself. Built-in first, catalog on failure (measured on the Redmi 9A).
- **One client per BROM:** a native session and an mtkclient workflow refuse each other; two clients corrupt both.
- **One plug cycle = one command** for mtkclient flows; the native session is the exception (boot once, then many operations).
- **Device validation is separate** from build/regression status. Never claim a throughput or success-rate gain without a measured flash.
- **Identity policy:** never decode, store or log the eMMC CID serial, UFS product/serial, ME_ID, SOC_ID or chip-unique ids. The eMMC part number is the only identity-adjacent field shown.
- **GPT cache:** only a table bound to the device's own geometry may be reused; an unbound table is refused/deleted.
- **Log display:** `DeviceClass - USBError(5, 'Input/Output Error')` must not appear in the app log (the raw transcript keeps it).
- **Never delete** `%LOCALAPPDATA%\PMKMobileTool\MediaTekSessions\seccfg-backup` or `archive-20261013`; never delete `hwparam.json` (device NV samples) or `port_trace.txt`.
- **Recipe handling:** master copy at `%LOCALAPPDATA%\PMKMobileTool\mtk\boot-profiles`; `CopyMtkBootRecipes` copies it into every build output; override with `-p:MtkRecipeSource=<folder>`.

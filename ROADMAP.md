Goal: grow PMK Unlocker toward the capability set of commercial multi-brand tools (Unlock Tool / DFT Pro / MST Tool).

Status date: **2026-10-28** (rewritten after the loader-catalog sprint; previous revision was 2026-10-27). 10. **MTK loader auto-detect** — `MtkDaCatalog.FindByChipset()` maps the chipset a BROM/DA session reports (`CPU: MT6765/MT8768t(…)`, falling back to `payloads/mt<code>_payload.bin`) to a catalog DA/Auth/Preloader. Each loader folder is scored by two independent signals: the DA blob's own chip code (`MTK_DOWNLOAD_AGENT` header, LE u16 at 0x6E — measured to equal the folder's MT token on every classic DA) and the MT token in the folder name; `MT6762→0x6761` and `MT6769→0x6768` family aliases are the only ones proven by a bundled DA. 27 chipsets resolve over the real catalog.
    **Applying it is failure-driven, not blind.** Device test on the Redmi 9A (2026-10-28) showed that when a foreign `MTK_AllInOne_DA` replaces mtkclient's own loader, mtkclient's xflash extension path dies: `DAconfig - Using custom loader: …\Infinix\MT6765_2\da.bin` → `DAXFlash - [LIB]: Error on boot to, addr: 0x4fff0000` → `DA Extensions failed to enable` → READ PARA failed, while every operation validated to date ran through that built-in path (mtkclient uploads its own `MTK_DA_V5.bin` and patches it: `Patching da1/da2`, `SBC patched to be disabled`, `DA Extensions successfully added`). So: Brand **"Auto Detect"** (default) detects and reports the matching loader but leaves `--loader` empty; if a session then fails on a loader/DA error and the catalog has a loader for that chip, the tool advances itself to Brand **"Auto + catalog DA"** (and the next run passes `--loader`); a catalog DA that cannot boot the DA extensions falls back to the built-in path the same way. Brand **"Auto + catalog DA"** can also be chosen up front. A hand-picked brand/model is never rewritten — the tool only warns when it contradicts the detected chip. Each switch prints the unplug/re-plug + re-run instruction rather than re-running a write itself.
    Detection runs **before** the BROM session too: ADB `Read Full Info` and `Detect` read `ro.soc.model` / `ro.board.platform`, and that token goes through the same resolver (`NoteMediaTekChipFromAdb`), so the MTK tab knows the chip and its loader candidate as soon as the phone is in Android. Detection is device-validated (Redmi 9A → `Infinix MT6765_2`, folder token and DA code both matched). Regression baseline is now **257 checks**.

## Primary gaps (what the commercial tools have that PMK lacks)

1. **Server-based auth bypass** (FRP / EDL / Mi-account / Samsung) — their real moat. Not code; requires OEM keys/partnerships. Local DA/auth files can go further than this doc used to assume, but SLA/DAA on MT6789/6853/6877+ still needs per-device auth or a server.
2. **Samsung Odin-protocol flash + server FRP** (PIT parsing is now done).
3. **Apple module** (iCloud / checkm8) — entirely absent.
4. **eMMC/UFS ISP** (pinout direct NAND) — advanced.
5. **Auto-detect + one-click flows** — MTK side is done: the chipset is taken from the BROM/DA session (`CPU: MT6765/MT8768t(…)`, `payloads/mt<code>_payload.bin`) **or** earlier from ADB (`ro.soc.model` / `ro.board.platform` on Read Full Info and Detect), resolved against the DA catalog, and the loader is applied automatically when mtkclient's own DA fails (or immediately on Brand "Auto + catalog DA"). Still missing: chipset from the USB-ID/BROM hwcode **without any command or ADB session at all** (e.g. a phone that never boots Android), the same auto-resolution for the QC loader catalog, and a single "detect → pick loader → run" flow instead of per-operation buttons.
6. **Device validation backlog** — MTK catalog mappings (all chipset-level reuse) and QC EFS/IMEI restore + Format All are code-complete but untested on real phones.
7. **Native QC coverage gap** — the native firehose session handles `printgpt`/`gpt`/`r`/`w`/`e`/`rl`/`reset`, but multi-partition flash, `--erase=frp`/`config` and the post-op reboot still shell out to `fh_loader.exe`; fold those onto the session so one loader/auth handshake serves the whole tab.
8. **No persistent MTK device session ("Boot Device")** — every MTK operation is its own `mtk.exe` process, and because the kamakiri/BROM path only attaches at USB enumeration the tool must demand an unplug/re-plug per operation (`EnsureMediaTekUnpluggedAsync`). Unlock Tool / DFT Pro boot the DA once and then read/write/erase any partition without touching the cable. Batched work already survives one plug cycle (`multi`/`script`, proven by the 22-partition scatter flash), but there is no interactive "device stays booted" mode. See **Phase 1.75**.

## Roadmap

### Phase 0 — Foundation
- Keep this gap list up to date. **Open business/legal decision:** the wired DA/auth/firehose blobs came from public packs with no license file (`Hamzaagsm/meer-tool-pro` has no LICENSE; `saidanimelek26/DA_mtk_FirehoseLoaders` likewise). They are OEM-signed MediaTek/Qualcomm blobs — decide whether to keep shipping them in a commercial tool, drop them, or source them legitimately.
- Decide whether to run an auth server (Phase 3) at all.

### Phase 1 — Deepen existing platforms (code-only, legally obtainable)
- **MTK:** ~~format-all~~, ~~IMEI read~~, ~~IMEI write~~, ~~DA/auth catalog~~ done. Remaining: arbitrary NV item repair, per-device auth coverage (Vivo/Tecno/Infinix DA-only entries), auth generation for SLA chipsets (e.g. SP Flash Tool DA → auth challenge extraction tooling), device validation of chipset-level mappings.
- **Qualcomm:** format userdata, real diag/QMI IMEI write, move the remaining `fh_loader` ops (multi-partition flash, `--erase=frp`/`config`, reboot) onto the native `FirehoseSession`.
- **Spreadtrum:** PAC format-all + NV read/write; FDL coverage only from named-device PAC firmware.
- **Samsung:** PIT-based multi-partition read (uses the existing PIT map), full partition read paths.

- Qualcomm: EFS backup → restore round-trip on a real SD device, then Format userdata.
- Report device results separately from `dotnet build` / regression status.

### Phase 1.75 — MTK "Boot Device": persistent DA session (Path B, chosen 2026-10-28)

Goal: press **Boot Device** once → the phone stays DA-booted on the cable → read / write / erase any partition interactively, like Unlock Tool's boot-device flow. Today every operation is a fresh `mtk.exe` process and the BROM/kamakiri path only attaches at USB enumeration, so the tool must demand an unplug per operation.

**B0 — the gate (RUN, logged verdict 2026-10-28 15:32–15:35).** Read-only probe: `%TEMP%\mtk-da-probe\probe2.ps1` → `probe2.log` (evidence kept; step outputs in `p2-out-*.txt` / `p2-err-*.txt`). Redmi 9A, no writes, PnP snapshot taken before and after every step.

Observed sequence:
- **Start state:** leftover enumeration from probe #1 — `MediaTek USB Port (VID_0E8D&PID_0003)`. Step A (`printgpt`) skipped BROM entirely, went straight into `DAXFlash`, got `Status error: Wrong magic`, then `USBError(5, 'Input/Output Error')` and `struct.error: unpack requires a buffer of 12 bytes`; "Error reading gpt". After A the device **disappeared** from PnP (the leftover DA died).
- **Step B (`printgpt`, no unplug):** mtkclient re-detected the phone by itself in **BROM/preloader** mode (`Detected regular mode`, `CPU: MT6765/MT8768t`), ran the full boot — kamakiri payload, xflash stage 1 from `MTK_DA_V5.bin`, da1/da2 patching, `SBC patched to be disabled`, stage 2, `DA Extensions successfully added at 0x4fff0000` — and printed the complete 43-partition GPT. **This step is the one that succeeded.** After B exited, the device re-enumerated as **`MediaTek DA USB VCOM (Android) (VID_0E8D&PID_2001)`** — the DA was still booted on the phone.
- **Step C (`r boot_para`, no unplug):** attached to that live DA and died again at the identical place — `mtk_da_handler.connect:128` → `mtk_daloader.reinit:192` → `xflash_lib.reinit:1009` → `get_ram_info:422` → `send_devctrl:194` → `status:140` → `struct.error: unpack requires a buffer of 12 bytes`. No `boot_para2.bin` produced. After C the device vanished again.

**Verdict (the "days, not weeks" branch is dead):**
1. The DA **does** survive the process exit at the electrical/USB level — the phone keeps the DA up and re-enumerates as the DA VCOM (`PID_2001`).
2. But mtkclient **cannot re-initialise a DA it did not upload**: on a fresh handle the `dev_ctrl` status reply is not the expected 12 bytes, so every "second process" dies in `xflash_lib.status()`. A keep-alive built on repeated `mtk.exe` invocations is therefore **not viable as-is**.
3. ⇒ "Boot Device" needs the **native C# MTK client (B1–B4)** — the weeks branch, not the session-state branch. Good news for that design: the DA stays up on its own, so a session we own from the boot onward has no reason to drop.
4. One cheap follow-up experiment inside B1 (do not re-run the probe for it): the failure is a *protocol* re-init, not a dead device — `libusb` **port reset + interface claim** before the first `dev_ctrl` may make a foreign-live DA answer again. Test it as the first thing in `MtkDaSession`; if it works, "Boot Device" can attach to an already-booted DA and B2 becomes optional.
5. Side finding, applies today: after a DA session dies the phone **re-enters BROM by itself** (step B proved it without any unplug) — so `EnsureMediaTekUnpluggedAsync` is stricter than the hardware requires; it can become a retry-and-re-detect rule instead of a hard demand.
6. Tooling note for any future probe: `Start-Process -PassThru` + `-RedirectStandardOutput` does **not** surface `ExitCode` here (the VERDICT lines printed `exit=` empty and mislabelled the successful step B as FAILED — the log body is the authoritative evidence). Use `& $exe args 2>&1` with `$LASTEXITCODE`, or parse the output text.

**Spike for that follow-up — built and armed 2026-10-28 15:55** (`%TEMP%\mtk-da-spike`: `spike.csproj` + `Program.cs` + `run.ps1`; x86 / net8.0-windows against the repo's own `libs\potato\LibUsbDotNet` + `libusb-1.0.dll`, kept outside the product tree until it has a verdict). It is read-only and sends no DA command: `S1` fresh `Open()` of `VID_0E8D&PID_2001`, `S2` descriptor + strings, `S3` interface/bulk-endpoint map, `S4` claim + idle bulk read, `S5` `ResetDevice()` (libusb port/device reset), `S6` re-open and read again after the reset. `run.ps1` sequences `printgpt` (boots the DA) → spike → `printgpt` (recoverability) in one plug cycle. **Awaiting the device run.**

**Known limit carried over:** a foreign `--loader` breaks mtkclient's own patched-DA path (see Constraints), so any session-keeper must keep using the DA mtkclient itself patches.

**B1 step-0 RESULT (run 2026-10-29 07:57–08:00, Redmi 9A, read-only) — the transport is NOT libusb.** The spike (`%TEMP%\mtk-da-spike`, rev 2 = raw P/Invoke against the repo's own 32-bit `libusb-1.0.dll`) measured:
- libusb **does** enumerate the leftover DA: `0E8D:2001 bus1/addr28`.
- `libusb_open()` on it returns **-12 `LIBUSB_ERROR_NOT_SUPPORTED`** — the port is owned by MediaTek's `wdm_usb` driver, which libusb's Windows backend will not take over.
- ~~There is **no libusb binary anywhere on this machine**~~ **CORRECTED 2026-10-29 (see the transport addendum below):** the claim was wrong — `mtk.exe` *does* carry libusb, just inside its PyInstaller archive, which is only unpacked to a temporary `_MEI*` folder while the process runs. What is true: mtkclient's reattach trace shows a transport that opened successfully and returned a short reply, and both MTK states are exposed to Windows as serial ports.
- Direct proof from .NET: `System.IO.Ports.SerialPort("COM37", 921600)` **opened the live DA VCOM** (DTR/RTS left off, 0 bytes pending, closed cleanly) — no admin, no driver install, no Zadig.
- Secondary finding: the leftover DA is **not guaranteed** — 3 of 4 `printgpt` exits left `PID_2001` visible in PnP, one exited with the device disappearing entirely, so a keeper cannot assume "attach later" even in principle.

**Consequence for the design:** `MediaTek/MtkDaSession.cs` should be built on `SerialPort` (the exact shape of `Qualcomm/FirehoseClient.cs`), not LibUsbDotNet — which removes the driver story and most of B1's risk. The open question moves to the protocol layer: **can a fresh serial host handshake a DA that another process booted?** (mtkclient's own answer was no: `struct.error: unpack requires a buffer of 12 bytes`.) That is now B1 step 1, and it is testable with nothing but a COM handle, a documented DA command frame and a raw reply hexdump — the framing must be derived from the public SP-Flash-Tool DA protocol and from the `da.bin` blobs we already ship, never from mtkclient source (GPL). If the attach handshake fails, "Boot Device" must own the boot too (B2) and the session is simply never released — still far simpler over serial than over libusb.

**Transport addendum (2026-10-29, device-free scan) — the transport is *measured*, not assumed.** A read-only inspection of the bundled `mtk.exe` (PyInstaller table-of-contents listing: entry names only, no module code read) showed it freezes **both** stacks: `libusb-1.0.dll` + `libusb32-1.0.dll` with pyusb backends (`usb.backend.libusb1`, `pyi_rth_usb`), **and** pyserial (`serial.serialwin32`, `serial.tools.list_ports_windows`). So the earlier "no libusb on the machine" reasoning was wrong, and which one drives the DA has to be measured on the wire. Two independent facts point at serial: Windows presents *both* MTK states as COM ports (`PID_0003` = "MediaTek USB Port_V1633 (COM3)", `PID_2001` = "MediaTek DA USB VCOM (COM37)"), and mtkclient's own log wording is "Waiting for PreLoader VCOM". The DA blob adds the frame vocabulary: magic `MTK_DOWNLOAD_AGENT` at offset 0, `MTK_AllInOne_DA_v3.3001…` at 0x20, and its own console strings `REVEIVING DEV CTRL CMD(0x%x)` / `REVEIVING CMD(0x%x)` — two frame classes (dev-ctrl and DA command). **Dead end worth recording:** the 4-char uppercase runs inside `da.bin` (`VHWI`, `YHZI`, `KCSC`, …) are **not** a command table — hexdump shows they are coincidentally printable bytes inside ARM Thumb code (`0x48e30`, `0xe5c0`; the "stride" is instruction size). Deriving the command list from blob strings does not work; the framing comes from the public SP-Flash-Tool protocol plus what the device answers.

**B1 step 1 — the decisive experiment (spike rev 3 built and armed 2026-10-29 08:18, `%TEMP%\mtk-da-spike`, driver `run2.ps1`, read-only):** while `mtk.exe r logo` is mid-transfer on the booted DA, ask .NET for the DA VCOM handle. **BUSY (open rejected) ⇒ mtkclient drives the DA through that COM port ⇒ `MtkDaSession` is a `SerialPort` session like `Qualcomm/FirehoseClient.cs` — no driver, no admin.** **FREE (open granted) ⇒ the VCOM is decorative and the DA lives on the libusb bulk path ⇒ the session must own the USB device before `wdm_usb` claims it, which is a driver story we do not want.** A second, purely passive step listens on the leftover DA port for unsolicited DA console bytes. Only after that verdict does step 1 send its first (read-only) handshake/status frame and hexdump the reply.

**B1 step 1 RUN 1 (2026-10-29 08:28:56–08:32:24, driver `run4.ps1` rev 6, Redmi 9A, read-only, `run4.log`) — result NOT USABLE, and here is the trap.** The cycle started with the phone already sitting on a leftover DA (`PID_2001`/COM37 visible before the launch), so `mtk.exe r cache` never went through BROM: it attached to the foreign DA, died ~2 s later (`ValueError: underlying buffer has been detached`, device then vanished from PnP — the 5th confirmation of B0's "cannot re-init a DA it did not upload", and the 6th of "a dead session drops back to BROM by itself"). The busy-check therefore produced `FREE 5 / BUSY 0 / GONE 1` **inside a dying attach, not inside a live stream** — the spike's own verdict line ("the VCOM is decorative, the DA runs on libusb bulk") is an over-claim and is *not* recorded as the transport answer. Recoverability was clean: the following `printgpt` re-booted from BROM (kamakiri → xflash stage 1/2 → DA extensions at 0x4fff0000) and printed the full 43-partition GPT, exit 0 — phone healthy, nothing written.

**B1 step 1 RUN 2 harness (built 2026-10-29 08:36, spike rev 4 + driver `run5.ps1`, build 0 warnings / 0 errors):** two fixes so the same mistake cannot repeat. (1) **Fresh-BROM gate** — the driver only launches the read when `VID_0E8D` is present *without* `PID_2001`, i.e. the phone must be in preloader/BROM; a leftover DA makes it wait and tell PMK to unplug. (2) **`--mode probe`** samples **both transports on the same tick** — a `SerialPort.Open()` classification (FREE/BUSY/GONE) *and* `libusb_open()` on every enumerated `0E8D` device with the numeric error name — and it keeps running until the COM port, the USB device **and** the mtk process are all gone; the driver then records whether `cache-spike.bin` reached the full 452 984 832 bytes, so a verdict can only be read next to proof of a real ~45 s stream. Four measurements follow from that table. (1) **A commercial Boot Device session is a libusb bulk session at its DA stage, not a serial one**: during the whole 65.8 s the DA was live the phone presented `VID_0E8D&PID_20FF`, Windows gave it **no COM port at all**, and plain `libusb_open` + `libusb_claim_interface(0)` both **succeeded** — i.e. the interface sits under a WinUSB-family binding that any libusb host can claim, with no driver install step we could observe. The protocol has **two layers with opposite endianness**, which is the single most important implementation fact:

- **Preloader/BROM = BIG-endian.** One command byte, echoed, then BE args, then a BE status: `fd`→HW code `0x0766`; `d4`+`10007000`+`00000001`→watchdog off; `d8`→target config `0xE7` (SBC/SLA/DAA/SWJTAG all True, mem read/write auth True, cmd `0xC8` blocked); `fe`/`ff`→`0x05`; `fc`→subcode `0x8a00`/HW ver `0xca00`/SW ver `0`; `fe`+`e1`→len `0x10`+ME_ID+status; `fe`+`e7`→len `0x20`+SOC_ID+status. Then **`Auth file is required`** → the kamakiri fork: ~50 repetitions of a `da`/`d1` spray against WDT `0x10007050` carrying the 612-B `mt6765_payload.bin` at `0x1009c0`. **It is a race, not a handshake**, and it is chipset-specific — and avoidable on devices where we hold a valid auth file. DA1 upload is `d7` + addr `0x200000` + len `0x39F98` + siglen `0x100`, then 512-B writes with no per-chunk ack, a 4-byte completion word, `d5` jump, and finally **`RX c0` = DA1 alive**.
- **DA = LITTLE-endian, magic `EF EE EE FE`.** Frame = `magic(4) + type u32le (always 1) + length u32le`, then `length` payload bytes. A command is a **4-byte frame carrying just the u32le command id**, then a status frame (`0` = OK), then an **argument frame**, then status, then (for reads) a data frame, then a **mandatory host ack frame** (`length=4`, payload `0`), then a final status. Sync is the ASCII `"SYNC"` (`53594e43`) sprayed with `0x10100(2,1,1,0,0)` and `0x10101(0)` until the DA answers `"SYNC"` back — the earlier stale-DA crash (`efeeeefe…` + `09000100`, 14 timeouts, `USBError(5)`) is exactly this sync hitting a dead DA.

Command ids observed (semantics taken from the log line mtkclient printed beside them): queries `0x40001` storage descriptor (104 B: type 1, block `0x200`, boot1/boot2 `0x400000`, RPMB `0x400000`, **u64 user `0xE8F800000`**), `0x40005` `"1.0"`, **`0x40007` transfer limits `0x200000`/`0x10000` — queried before every read**, `0x40008` 16-B chip id, `0x4000a` `"brom"`, **`0x4000b` `"high-speed"`**, `0x4000c` 48-B layout, `0x4000d` HW/SW ver, `0x40011` DA build `0xC0010004`, `0x40016` SLA status; operations `0x10005` **READ FLASH**, `0x10008` **upload+jump** (u64le addr, u64le len — DA2 at `0x40000000`/331916 B, extensions at `0x4FFF0000`/16428 B, both answered with `"SYNC"`), `0x10009` no-arg preamble issued 31× before every op group, `0x1000a` EMI/DRAM data (1712 B, `MTK_BLOADER_INFO_v35`); extensions `0xF0000`→sentinel `0xA1A2A3A4`, `0xF0005(0)`. Unidentified but recorded: `0x20003(0)`, `0x20004(0x68)`.

**READ FLASH is fully specified and was exercised 15 times.** Command `0x10005`, then a **56-byte argument struct**: `u32le region=1`, `u32le ?=8` (constant, purpose unknown), `u64le offset`, `u64le length`, 32 zero bytes. The GPT cycle read `0x0/0x400`, `0x600/0x200`, `0x200/0x400` (returned `4546492050415254` = "EFI PART"), ten `0x200` sectors of the entry array, and finally **`0x0/0x4200` = 16896 bytes in ONE data frame**. Two implementation facts follow: **the DA does not chunk at the protocol level** (512-B USB packets are invisible above the stream, so a `SerialPort` loop of "read 12, then read `length`" is correct), and **the host ack comes once after the whole payload** — omitting it is the most likely way to desynchronise a session. *(Both of those two facts were over-generalisations from a sample in which every read was ≤ 16896 B, i.e. below the DA's own packet limit — RUN 8 below measured an 8 MiB read and corrected them.)*

3. `MediaTek/MtkDaSession.cs` is the boot machine over a transport-agnostic `IMtkTransport`. Replies are verified by class, not uniformly: `echo` byte-compared, `zero` status must stay zero, `len` replies (registers, RAM, ME_ID/SOC_ID, versions) have their **length** verified and their content deliberately ignored so a second unit of the same model still boots, and `token` replies (`hw-code`, `da-alive` 0xc0, `sync`) are the frames whose value *is* the meaning — a wrong HW code stops the boot with "replaying a bypass spray on the wrong chipset is how phones get bricked". BROM's 0xc0 gate (`_da1Alive`) is separate from `DaIsReady`, so the DA stage cannot start on a device that never acknowledged the jump.
4. `MediaTek/MtkDaTransport.cs` is the serial half: `SerialPort` on the MTK VCOM plus `MtkVcom`/`MtkVcomPort`, which resolves the port from `Win32_PnPEntity` under **VID_0E8D only** — the old single-COM-port fallback is gone, and two candidates is a refusal, not a guess. The PID is only used to find the port; the recipe's own HW-code and 0xc0 checks decide what the device really is, which is the RUN 6 lesson about a stale DA lying about BROM.

Verified without a phone: **85 new regression checks** (342 total, Release build 0/0), covering both codecs, the 56-byte extent struct, the `0x40007` limits reply, the additive byte-sum, a 22-case recipe-refusal matrix, and a scripted fake `IMtkTransport` that replays the recorded recipe — the boot machine puts **exactly 29 writes / 173 bytes** on the wire in recipe order and aborts on each of the eight disagreement paths. One capture-derived bug was found while pinning the decode: `MtkBrom.DescribeConfig` had three of the nine target-config flags printed with the wrong sense; it now reproduces the working client's own nine lines for `0xE7` (SWJTAG, RootCert and CmdC8Blocked are the inverted ones).

Still open before this path replaces `mtk.exe`: the **device run** (port settings — 115200 8N1, DTR on, RTS off — are a choice, not an observation, so a real boot has to confirm them), whether the DA stage stays on the same COM face after the jump (RUN 6's own log shows the client never reopening a port, and its SYNC reply arrives *after* a timeout, which is why the machine waits per expectation instead of per command), the licensing decision that would let the extracted DA/EMI images ship inside `mtk/boot-profiles` (they are still only in the spike tree, so a shipped build has no recipe and fails closed), and B3 (READ/WRITE/ERASE on top of `WriteFrame`/`ReadFrameAsync`).

**Licensing (must decide before B1):** **DECIDED 2026-10-28 — PMK chose the clean-room route.** mtkclient is **GPL-3.0**. Shelling out to `mtk.exe` keeps that at arm's length, but writing `MtkDaSession` by translating its Python source would make our exe a derivative work. The clean-room route is to implement the DA command framing from MediaTek's own SP-Flash-Tool protocol (publicly documented and independently reimplemented), not from mtkclient code — so B1 is written against LibUsbDotNet/libusb primitives and the public protocol description only, and nobody reads mtkclient's `xflash_*` sources while doing it. The bundled `payloads/*.bin` are mtkclient-distributed binaries — same question as the OEM DA blobs in Phase 0.

**Cost estimate:** B1–B3 is a multi-week effort with real bricking risk on the boot stage. B0 ran on 2026-10-28 and its verdict is logged above: the DA survives a process exit but mtkclient cannot re-init it, so the shortcut (a session-state-only "Boot Device" on top of `mtk.exe`) is **ruled out** — the native client is the way, and it must be started only after the licensing decision below.

## Constraints

- OEM-signed loaders/auth keys (DA_AUTH, Firehose programmers, FDL) are proprietary; source them legally or not at all. The current packs are unlicensed re-hosts — see Phase 0.
- `bundled-tools/`, `tools/` and `edl/` are gitignored; the only rollback reference for loader binaries is `bundled-tools/integrity.json` + `dependency-lock.json`. After any loader change: `scripts/make_tool_integrity.ps1` → sync `bundledInventory.sha256`/`entries` → Release build → `scripts/verify_qc_loaders.ps1`.
- Never copy a differently-named Common DA into an existing loader folder — it silently replaces a working DA; hash-check against the seed first.
- Device validation must stay separate from build/regression verification (see `tests/Regression`; 664 checks is the current baseline).
- MTK: never auto-pass a catalog `--loader` over mtkclient's built-in DA as the default — the xflash DA-extension patch path only works with the DA mtkclient bundles itself (measured on Redmi 9A). Built-in first, catalog on failure.
- mtkclient is GPLv3: keep it at arm's length as a subprocess. A native MTK session (Phase 1.75) must be written clean-room from the MediaTek SP-Flash-Tool protocol, never translated from mtkclient source. The B0 gate is closed (verdict logged 2026-10-28: mtkclient cannot reuse a DA it did not boot, so only a native client can deliver "Boot Device") — the remaining precondition for B1 is the GPL licensing decision.
- Never delete `%LOCALAPPDATA%\PMKMobileTool\MediaTekSessions\seccfg-backup` or its `archive-20261013`; never delete `hwparam.json` (device NV samples) or `port_trace.txt`.
- Do not claim throughput or success-rate gains without a measured flash on a real device.
